爬虫初始

爬虫相关介绍

  • 什么是爬虫?

    • 爬虫程序是需要充当B/S或者C/S架构中的客户端。
    • 爬虫程序需要模拟客户端进行请求发送，然后获取服务器端对应的相关数据。
    • 在B/S架构中爬虫程序模拟的就是浏览器。

  • 提问：如果日后你的爬虫程序没有爬取到你想要的数据，why？

    • 爬虫程序模拟浏览器的力度不够。

  • 爬虫在应用场景的分类?

    • 通用爬虫：可以将一个页面中所有的数据都爬取到。
    • 聚焦爬虫：建立在通用爬虫基础之上。可以将一张页面中局部、指定的数据进行抓取
    • 增量式爬虫：可以监测网站数据更新的情况。以便将最新更新出来的数据进行抓取

  • 爬虫的矛与盾（重点）?

    • 反爬机制：作用在门户网站中，网站会指定出一些阻止爬虫程序进行数据爬取的机制。
    • 反反爬策略：作用在爬虫程序中，可以指定破解反爬机制的策略，这些策略就是反反爬策略。

爬虫合法性探究

  • 爬虫作为一种计算机技术就决定了它的中立性，因此爬虫本身在法律上并不被禁止，但是利用爬虫技术获取数据这一行为是具有违法甚至是犯罪的风险的。所谓具体问题具体分析，正如水果刀本身在法律上并不被禁止使用，但是用来捅人，就不被法律所容忍了。
  • 或者我们可以这么理解：爬虫是用来批量获得网页上的公开信息的，也就是前端显示的数据信息。因此，既然本身就是公开信息，其实就像浏览器一样，浏览器解析并显示了页面内容，爬虫也是一样，只不过爬虫会批量下载而已，所以是合法的。不合法的情况就是配合爬虫，利用黑客技术攻击网站后台，窃取后台数据（比如用户数据等）。
  • 举个例子：像谷歌这样的搜索引擎爬虫，每隔几天对全网的网页扫一遍，供大家查阅，各个被扫的网站大都很开心。这种就被定义为“善意爬虫”。但是像抢票软件这样的爬虫，对着 12306 每秒钟恨不得撸几万次，铁总并不觉得很开心，这种就被定义为“恶意爬虫”。
  • 爬虫所带来风险主要体现在以下3个方面：
    • 1、违反网站意愿，例如网站采取反爬措施后，强行突破其反爬措施；
    • 2、爬虫干扰了被访问网站的正常运营；
    • 3、爬虫抓取了受到法律保护的特定类型的数据或信息。
  • 那么作为爬虫开发者，如何在使用爬虫时避免进局子的厄运呢？
    • 1、在规避反爬虫措施的同时，需要优化自己的代码，避免干扰被访问网站的正常运行；
    • 2、在使用、传播抓取到的信息时，应审查所抓取的内容，如发现属于用户的个人信息、隐私或者他人的商业秘密的，应及时停止并删除。
  • 总结：
    • 可以说在我们身边的网络上已经密密麻麻爬满了各种网络爬虫，它们善恶不同，各怀心思。而越是每个人切身利益所在的地方，就越是爬满了爬虫。所以爬虫是趋利的，它们永远会向有利益的地方爬行。技术本身是无罪的，问题往往出在人无限的欲望上。因此爬虫开发者的道德自持和企业经营者的良知才是避免触碰法律底线的根本所在。

1.1、HTTP协议

1.1.1 、http协议简介

HTTP协议是Hyper Text Transfer Protocol（超文本传输协议）的缩写,是用于服务器与本地浏览器之间传输超文本的传送协议。

超文本：超文本就是指“含有指向其他资源链接”内容的文本。大概就是，不仅仅是文字，还有多媒体：视频、图片、动画等。

协议：HTTP协议就是服务器（Server）和客户端（Client）之间进行数据交互（相互传输数据）的一种形式。我们可以将Server和Client进行拟人化，那么该协议就是Server和Client这两兄弟间指定的一种交互沟通方式。大家都看过智取威虎山中杨子荣和土匪们之间说的黑话吧：

1.1.2、 http协议特性

基于请求－响应模式

HTTP协议规定,请求从客户端发出,最后服务器端响应该请求并返回。换句话说,肯定是先从客户端开始建立通信的,服务器端在没有接收到请求之前不会发送响应

无状态(重要)

HTTP协议自身不对请求和响应之间的通信状态进行保存。每当有新的请求发送时,就会有对应的新响应产生。协议本身并不保留之前一切的请求或响应的相关信息。这是为了更快地处理大量事务,确保协议的可伸缩性,而特意把HTTP协议设计成如此简单的。

状态可以理解为客户端和服务器在某次会话/通信中产生的数据，那无状态的就以为这些数据不会被保留。如果会话中产生的数据是我们需要保存的，也就是说要“保持状态”。

可是,随着Web的不断发展,因无状态而导致业务处理变得棘手的情况增多了。比如,用户登录到一家购物网站,即使他跳转到该站的其他页面后,也需要能继续保持登录状态。网站为了能够掌握是谁送出的请求,需要保存用户的状态。

HTTP/1.1虽然是无状态协议,但为了实现期望的保持状态功能, 于是引入了Cookie技术。有了Cookie再用HTTP协议通信,就可以管理状态了。有关Cookie的详细内容稍后讲解。

http协议包含由浏览器发送数据到服务器需要遵循的【请求协议】与服务器发送数据到浏览器需要遵循的【响应协议】。

1.1.3、http请求协议与响应协议

用于HTTP协议交互的信息被称为HTTP报文。请求端(客户端)的HTTP报文叫做请求报文,响应端(服务器端)的叫做响应报文。HTTP报文本身是由多行数据构成的字文本。

(1) 请求协议（重要）

  • 请求头/报文头：

    • 请求头中存储的是该请求的一些主要说明（自我介绍）。服务器据此获取客户端的信息。

    • ```
      accept:浏览器通过这个头告诉服务器，它所支持的数据类型
      Accept-Charset: 浏览器通过这个头告诉服务器，它支持哪种字符集
      Accept-Encoding：浏览器通过这个头告诉服务器，支持的压缩格式
      Accept-Language：浏览器通过这个头告诉服务器，它的语言环境
      Host：浏览器通过这个头告诉服务器，想访问哪台主机
      If-Modified-Since: 浏览器通过这个头告诉服务器，缓存数据的时间
      Referer：浏览器通过这个头告诉服务器，客户机是哪个页面来的 防盗链
      Connection：浏览器通过这个头告诉服务器，请求完后是断开链接还是何持链接
      X-Requested-With: XMLHttpRequest 代表通过ajax方式进行访问
      User-Agent：请求载体的身份标识

  • 响应体：

    • 根据客户端指定的请求信息，发送给客户端的指定数据

  • 响应状态码：

    • 状态码指的是是当客户端向服务器端发送请求时, 返回的请求结果。借助状态码,用户可以知道服务器端是正常受理了请求,还是出现了什么问题错误 。

1.2、Cookie概述

1.2.1 COOKIE的由来

  • 大家都知道HTTP协议是无状态的。
    • 状态可以理解为客户端和服务器在某次会话中产生的数据，那无状态的就以为这些数据不会被保留。每当有新的请求发送时,就会有对应的新响应产生。协议本身并不保留之前一切的请求或响应的相关信息。
    • 一句有意思的话来描述就是人生只如初见，对服务器来说，每次的请求都是全新的，及时同一个客户端发起的多个请求间。随着Web的不断发展,因无状态而导致业务处理变得棘手的情况增多，因此我们需要解决这个问题，也就是说要让http可以“保持状态”，那么Cookie就是在这样一个场景下诞生。

1.2.2 什么是cookie

  • 首先来讲，cookie是浏览器的技术，Cookie具体指的是一段小信息，它是服务器发送出来存储在浏览器上的一组组键值对，可以理解为服务端给客户端的一个小甜点，下次访问服务器时浏览器会自动携带这些键值对，以便服务器提取有用信息。

记住：cookie表示的键值对数据是由服务器创建，且存储在客户端浏览器中。

1.2.3 cookie的原理（重点）

  • cookie的工作原理是：

    • 浏览器访问服务端，带着一个空的cookie，然后由服务器产生内容，浏览器收到相应后保存在本地；
    • 当浏览器再次访问时，浏览器会自动带上Cookie，这样服务器就能通过Cookie的内容来判断这个是“谁”了。
    • cookie的内容是有服务器自主设计的，客户端无法干涉！

  • 注意，不同浏览器之间是不共享Cookie的。也就是说在你使用IE访问服务器时，服务器会把Cookie发给IE，然后由IE保存起来，当你在使用FireFox访问服务器时，不可能把IE保存的Cookie发送给服务器。

2.1、 HTML概述

  • HTML，即超文本标记语言（HyperText Markup Language ]），也可叫做web页面。扩展名是 .html 或是 .htm 。

  • HTML，是一种用来制作网页的标准标记语言。超文本，指的就是超出普通文本范畴的文档，可以包含文本、图片、视频、音频、链接等元素。

  • HTML 不是一种编程语言，而是一种写给网页浏览器、具有描述性的标记语言。

也就是说：使用HTML语言描述的文件，需要通过网页浏览器显示出效果。用户在访问网页时，是把服务器的HTML文档下载 到本地客户设备中，然后通过本地客户设备的浏览器将文档按顺序解释渲染成对应的网页效果。

网页本身是一种文本文件，通过在文本文件中添加各种各样的标记标签，可以告诉浏览器如何显示标记中的代表的内容，如：HTML中有的标签可以告诉浏览器要把字体放大，就像word一样，也有的标签可以告诉浏览器显示指定的图片，还有的标签可以告诉浏览器把内容居中或者倾斜等等。

每一个HTML标签代表的意义都不一样。同样，他们在浏览器中表现出来的外观也是不一样的。

2.5、超链接标签

2.5.1、超链接基本使用

Jenkins的主节点是整个Jenkins系统的核心，负责管理任务、调度构建和监控整个系统的状态。
代理节点（Agent）：
代理节点是Jenkins系统中的工作节点，负责执行具体的构建任务。主节点可以分配任务给一个或多个代理节点，实现分布式构建，提高系统的扩展性。
任务（Job）：
任务是Jenkins中一个具体的构建单元，它定义了构建、测试或部署等具体操作的步骤和配置。
构建（Build）：
构建是指将源代码转换为可执行软件或其他部署单元的过程。构建过程通常包括编译、单元测试、打包等操作。
流水线（Pipeline）：
流水线是Jenkins中的一种抽象概念，是一组用于定义整个软件交付流程的代码。Jenkins Pipeline允许用户以代码的形式定义整个构建、测试和部署过程，从源代码到最终交付的全过程都可以通过Pipeline进行管理和监控。
Pipeline的作用和与传统方式的区别：
Pipeline的作用：
持续交付和集成：
Jenkins Pipeline的主要作用是实现持续交付和集成，将整个软件开发和交付流程以代码的形式进行定义，从源代码到最终交付的全过程都可以通过Pipeline进行管理和监控。
可视化和可控性：
Pipeline提供了一个可视化的界面，可以清晰地查看整个流水线的执行情况，同时也提供了更高级的控制和定制能力，支持复杂的构建和部署场景。
与传统构建和部署方式的区别：
可维护性：
传统方式中，构建和部署的步骤通常分散在不同的配置文件或脚本中，难以维护。而Pipeline通过代码形式定义，使得构建流程更加结构化、可读性更高，易于维护和更新。
可重用性：
Pipeline的代码可以被重复使用，允许团队将通用的构建和部署逻辑进行封装，以便在不同的项目中共享和重用。
强大的控制流程：
传统方式中，构建和部署的控制流程通常较为简单，而Pipeline支持丰富的控制流程，包括条件判断、循环等，使得构建流程更加灵活和强大。
可视化和审计：
Pipeline提供了可视化的界面，方便团队成员和管理者查看整个流水线的执行状态。同时，Pipeline也支持审计和记录，可以追踪整个流水线的执行历史。
通过引入Pipeline，Jenkins使得构建和部署的过程更加可控、可维护，并支持持续集成和交付的最佳实践。

在Jenkins中，什么是一个Agent？它的作用是什么，以及它与Jenkins Master的关系是什么？
在Jenkins中，一个Agent（代理节点）是用于执行构建任务的工作节点。代理节点是Jenkins系统的一部分，它接收来自主节点（Master）的指令，并在本地执行构建过程。代理节点的存在使得Jenkins能够实现分布式构建，将任务分发到不同的节点上并行执行，从而提高系统的扩展性和构建的效率。
代理节点的作用包括：
执行构建任务：
代理节点负责执行由主节点分配的具体构建任务。这包括从版本控制系统中检出源代码、执行构建脚本、运行测试等。
提供环境：
代理节点提供了一个独立的执行环境，包括操作系统、依赖库和工具，确保构建过程在一个隔离的环境中运行。
分布式构建：
代理节点使得Jenkins能够实现分布式构建，即将不同的构建任务分配到不同的节点上并行执行，从而加速构建过程。
代理节点与Jenkins Master的关系：
通信协议：
代理节点与主节点之间通过一种特定的通信协议进行通信，通常使用JNLP（Java Network Launch Protocol）或SSH（Secure Shell）协议。
指令接收：
主节点负责分配任务，并将构建的指令发送到代理节点。代理节点接收这些指令并在本地执行相应的构建步骤。
状态报告：
代理节点会定期向主节点报告构建的状态，包括构建的进度、日志输出等信息。这使得主节点能够实时监控构建过程。
节点配置：
主节点负责管理和配置代理节点。管理员可以在Jenkins中添加、移除、配置代理节点，并决定哪些任务应该在哪个节点上执行。
可扩展性：
通过使用代理节点，Jenkins实现了分布式构建，使得系统更容易扩展，可以在需要时添加新的代理节点来应对不断增长的构建需求。
总体而言，代理节点在Jenkins中起到了执行构建任务的关键作用，通过分布式构建的方式，有效地提高了构建的并行性和整体性能。

如何在Jenkins中实现持续集成（CI）？可以简要描述一下典型的CI流水线是什么样的吗？
在Jenkins中实现持续集成（Continuous Integration，CI）通常涉及设置一个构建任务，并在代码仓库中的每次提交或定期触发构建。以下是典型的CI流水线的一般步骤：
典型的CI流水线步骤：
代码提交：
开发人员向版本控制系统（例如Git）提交代码变更。
触发构建：
Jenkins通过轮询版本控制系统或通过Webhook接收到代码变更的通知，触发构建任务。
拉取代码：
构建任务开始时，Jenkins从版本控制系统中拉取最新的代码。
编译：
对代码进行编译，生成可执行文件或其他构建产物。这一步通常包括检查语法错误、编译源代码等。
单元测试：
执行单元测试，确保代码变更不会导致现有功能的破坏。单元测试通常是自动运行的测试脚本。
集成测试：
执行集成测试，验证各个模块之间的协同工作。这可能包括测试API、服务端点等。
静态代码分析：
进行静态代码分析，检查代码质量、风格和潜在的问题。可以使用工具如SonarQube等。
构建产物：
如果构建成功，生成构建产物（例如JAR、WAR文件等）。
部署到测试环境：
将构建产物部署到测试环境，以进行进一步的集成测试或手动测试。
通知：
向相关团队成员发送构建状态和测试结果的通知，可以通过邮件、Slack等渠道。
CI流水线的优势：
早期发现问题：
通过频繁地构建和测试，能够在代码集成时及早发现和解决问题，减少集成阶段的错误。
自动化流程：
CI流水线可以自动执行整个构建和测试过程，减少手动操作，提高效率。
快速反馈：
开发人员可以快速获得构建和测试的反馈，使其能够更快速地修复问题。
可重复性：
CI流水线确保每次构建都是在相同的环境中进行，保证了构建的可重复性。
版本控制集成：
CI流水线与版本控制系统紧密集成，可以根据代码的变更触发构建，确保每次提交都能够进行测试。
通过建立有效的CI流水线，团队能够更好地管理和交付代码，确保软件质量和稳定性。

如何在Jenkins中实现自动化部署？你可以谈谈Blue-Green Deployment和Canary Deployment的区别吗？
在Jenkins中实现自动化部署通常涉及使用插件或脚本执行构建产物的部署操作。以下是一般的自动化部署步骤：
自动化部署步骤：
构建任务配置：
在Jenkins中配置构建任务，确保构建过程生成所需的构建产物（例如：JAR、WAR文件）。
构建产物存储：
将构建产物存储在一个可访问的位置，如Artifactory、Nexus或直接在版本控制系统中的特定目录。
部署任务配置：
创建一个新的Jenkins任务用于部署。该任务应该配置为在构建成功后自动触发。
部署脚本或插件：
在部署任务中，使用Shell脚本、SSH插件或专用的部署插件执行构建产物的部署操作。这可能涉及将产物复制到服务器、启动服务、更新数据库等。
配置参数化部署：
使用参数化构建或环境变量，使得部署任务能够根据不同的环境（开发、测试、生产等）进行不同的部署。
集成通知：
集成通知机制，例如Slack通知或邮件通知，以便及时了解部署的状态和结果。
Blue-Green Deployment和Canary Deployment的区别：
Blue-Green Deployment（蓝绿部署）：
特点：
两个环境，一个是当前生产环境（Blue），另一个是新版本的环境（Green）。
流程包括在新环境中部署和测试新版本，然后将流量从蓝色环境切换到绿色环境。
优点：
零宕机部署，用户在切换时不受影响。
可以轻松回滚到蓝色环境，降低风险。
缺点：
需要维护两个完整的环境，可能带来额外的成本。
Canary Deployment（金丝雀部署）：
特点：
将新版本逐步引入生产环境，只在小部分服务器或用户中使用新版本。
通过逐步扩大新版本的使用范围，以确保新版本稳定。
优点：
可以快速发现潜在问题，避免影响所有用户。
允许在生产环境中逐步发布，减轻风险。
缺点：
需要更复杂的监测和流量管理机制。
部署过程可能较慢。
选择Blue-Green Deployment还是Canary Deployment取决于具体的需求和项目特点。通常，Blue-Green适用于需要零宕机和快速回滚的情况，而Canary适用于希望逐步发布并控制风险的情况。

在Jenkins中如何处理构建过程中的依赖关系？是否有任何策略可以提高构建效率并减少依赖问题？
在Jenkins中处理构建过程中的依赖关系是关键的一步，可以通过一些策略来提高构建效率并减少依赖问题。以下是一些建议：
依赖管理工具：
使用依赖管理工具，如Maven、Gradle或npm（对于Node.js项目）。这些工具可以自动下载和管理项目依赖，确保构建过程中所需的库和工具是可用的。
局部缓存：
设置局部缓存以存储构建过程中下载的依赖。这可以显著减少对远程存储库的依赖，提高构建速度。Maven和Gradle等构建工具都支持局部缓存。
使用构建工具的缓存机制：
大多数构建工具都提供缓存机制，可以在多次构建之间共享依赖项。例如，Maven的本地仓库就是一个缓存机制，可以在不同项目之间共享已下载的依赖项。
Artifact Repository：
设置Artifact Repository（如Artifactory、Nexus等）来存储项目产物和依赖项。这样可以确保构建过程中所需的依赖项是可靠和稳定的，不受外部仓库的影响。
并行构建：
如果项目结构允许，考虑并行构建。通过将项目拆分为独立的模块，可以在并行处理它们，从而加快整体构建时间。Jenkins的Pipeline功能支持定义并行阶段。
缓存Docker镜像：
如果项目使用Docker，可以缓存Docker镜像，避免在每次构建时重新拉取完整的镜像。这可以通过Docker Layer的缓存机制来实现。
定期清理不必要的依赖：
定期清理不再使用的依赖项，以避免构建环境中积累过多的不必要文件。可以使用构建脚本或工具来自动化这个清理过程。
预构建镜像：
如果构建过程中涉及到比较庞大的依赖项，考虑使用预构建的基础镜像。这样可以在构建过程中直接使用已经包含了依赖项的镜像，而无需重新下载。
这些策略可以帮助提高构建效率并减少依赖问题。根据项目的具体情况选择合适的策略，以确保构建过程的稳定性和高效性。

Docker的基本概念：
请解释Docker是什么，以及它是如何工作的？谈谈Docker的基本概念。
Docker是什么：
Docker是一种容器化平台，用于轻松打包、分发和运行应用程序。它利用容器技术，将应用程序和其所有依赖项封装到一个独立的容器中，使得应用程序在任何环境中都能够一致地运行。
Docker的基本概念：
容器（Container）：
容器是一个轻量级的、独立运行的软件包，包含应用程序及其所有依赖项，如代码、运行时、系统工具、库等。容器隔离了应用程序及其环境，确保应用程序在不同的环境中运行一致。
镜像（Image）：
镜像是一个只读的模板，包含创建容器所需的文件系统、应用程序代码、运行时、库和设置。镜像是用于构建容器的基础。用户可以从现有的镜像构建自己的应用程序镜像，也可以通过仓库分享和获取镜像。
仓库（Repository）：
仓库是用于存储和组织镜像的地方。它可以位于本地主机或远程服务器。Docker Hub是一个公共的仓库，用于存储和分享镜像，而用户也可以创建私有仓库。
Dockerfile：
Dockerfile是一个文本文件，包含用于构建Docker镜像的指令。通过定义Dockerfile，用户可以自动化镜像的构建过程，确保镜像的可重复性和一致性。
容器编排：
容器编排是一种用于管理和协调多个容器的技术。Docker提供了多种容器编排工具，如Docker Compose、Docker Swarm和Kubernetes，使得用户能够在多个容器之间定义关系、调度和扩展。
Docker Daemon和Docker Client：
Docker Daemon是在主机上运行的后台进程，负责管理Docker容器。Docker Client是与Docker Daemon通信的命令行工具，用户通过Docker Client与Docker Daemon交互，执行各种Docker命令。
Docker是如何工作的：
Docker利用Linux内核中的容器技术，主要包括cgroups和namespace，以实现轻量级、快速和可移植的虚拟化。Docker将应用程序及其依赖项封装到一个容器中，并提供一致的运行时环境，无论在何处运行，都能保持一致性。容器可以在同一主机上的不同命名空间中运行，使得它们相互隔离，同时仍然共享主机操作系统的内核。
基于Docker的工作流程包括以下步骤：
用户定义Dockerfile，描述如何构建镜像。
Dockerfile通过Docker Client发送给Docker Daemon。
Docker Daemon根据Dockerfile构建镜像，其中包括应用程序和其依赖项。
构建的镜像存储在本地主机或远程仓库中。
用户使用Docker Client启动容器，该容器基于特定的镜像。
Docker Daemon创建并运行容器，提供一个隔离的运行时环境。
Docker的这种容器化方法带来了许多好处，包括更快的部署、更高的可移植性、更有效的资源利用以及简化的开发和运维流程。

Docker容器和虚拟机的区别：
请比较Docker容器和虚拟机，以及它们之间的主要区别是什么？
Docker容器和虚拟机（VM）都是用于虚拟化的技术，但它们之间存在一些关键的区别。以下是Docker容器和虚拟机之间的比较：

  1. 隔离性和资源利用：
    Docker容器：
    共享宿主操作系统的内核，容器之间使用Linux namespace进行隔离。这使得容器轻量级，启动速度快，且占用的资源较少。
    虚拟机：
    每个虚拟机都有自己的完整操作系统，包括独立的内核。虚拟机之间的隔离更为彻底，但也导致更大的资源占用和启动时间较长。
  2. 资源占用和启动时间：
    Docker容器：
    使用主机操作系统的内核，容器共享主机的内存和CPU资源。由于轻量级，容器启动非常快，并且占用较少的硬盘空间。
    虚拟机：
    每个虚拟机都包含一个完整的操作系统，占用的资源相对较多。虚拟机的启动时间通常较长，并且需要更多的硬盘空间。
  3. 运行环境和可移植性：
    Docker容器：
    由于容器共享主机内核，因此在不同环境中运行的一致性更高。容器可以在开发、测试和生产环境中更容易地迁移和部署。
    虚拟机：
    虚拟机包含自己的内核和操作系统，因此在不同环境中可能需要更多的配置和调整。虚拟机的迁移和部署相对复杂。
  4. 性能：
    Docker容器：
    由于共享主机内核，容器通常具有更好的性能和较低的开销。容器可以更有效地利用系统资源。
    虚拟机：
    由于每个虚拟机都有独立的操作系统，会产生额外的开销。在高密度环境中，虚拟机可能需要更多的资源。
  5. 安全性：
    Docker容器：
    容器之间的隔离主要依赖于Linux namespace和cgroups，虽然提供了一定的隔离性，但在一些极端情况下可能存在一些安全风险。
    虚拟机：
    每个虚拟机有独立的内核，提供了更强的隔离性。虚拟机通常被认为具有更高的安全性。
    总体来说，Docker容器更适合轻量级、快速部署和高效资源利用的场景，而虚拟机更适合需要更严格隔离和独立操作系统的场景。在实际应用中，通常根据项目需求和资源利用效率来选择使用Docker容器或虚拟机。

Docker镜像是什么，如何创建和使用它们？
请解释Docker镜像是什么，以及如何创建、推送和拉取Docker镜像？
Docker镜像是什么：
Docker镜像是一个轻量级、可执行的软件包，包含运行应用程序所需的所有内容，包括代码、运行时、库、环境变量和配置文件。Docker镜像是容器的基础，容器是由Docker镜像创建的运行实例。镜像是一个只读的模板，用于创建和启动容器，并确保容器在不同环境中的一致性。
Docker镜像的创建、推送和拉取：

  1. 创建Docker镜像：
    Docker镜像的创建通常通过编写一个Dockerfile来实现，Dockerfile是一个文本文件，包含一系列指令，用于描述如何构建镜像。以下是一个简单的Dockerfile示例：

    使用基础镜像

    FROM ubuntu:latest

设置工作目录

WORKDIR /app

复制本地文件到容器

COPY . .

安装应用程序依赖

RUN apt-get update && apt-get install -y python3

定义容器启动时执行的命令

CMD [“python3”, “app.py”]
在Dockerfile所在的目录中运行以下命令构建镜像：
docker build -t my-python-app .
这将使用当前目录下的Dockerfile构建一个名为 my-python-app 的镜像。
2. 推送Docker镜像到仓库：
要将镜像推送到Docker仓库（如Docker Hub），首先需要登录到仓库：
docker login
然后，使用以下命令将镜像推送到仓库：
docker push username/my-python-app
其中，username 是你在Docker Hub上的用户名。
3. 拉取Docker镜像：
要从仓库拉取镜像，可以使用以下命令：
docker pull username/my-python-app
这将从Docker Hub上的仓库中拉取 my-python-app 镜像。
总体来说，通过使用Dockerfile定义构建步骤，通过docker build命令创建镜像，然后通过docker push将镜像推送到仓库。其他团队成员可以通过docker pull命令拉取这个镜像，以便在其本地环境中运行相同的应用程序。这种方式使得在不同环境中共享和部署应用程序变得更加简单和可靠。

- “8080:80”

一键停止和清理：

Docker网络：
谈谈Docker的网络模式，包括默认网络、桥接网络和覆盖网络。如何在容器之间进行通信？
Docker提供了多种网络模式，用于在容器之间进行通信。以下是Docker的主要网络模式：

  1. 默认网络（bridge network）：
    默认情况下，当创建一个新容器时，Docker会将其连接到名为
    bridge

  2. 桥接网络（bridge network）：
    Docker桥接网络允许用户创建自定义的桥接网络，并将容器连接到这个网络。桥接网络与默认网络类似，但用户可以自定义网络的名称、子网和网关。通过创建桥接网络，容器可以在同一网络中相互通信，而不需要进行端口映射。
    docker network create my-bridge-network
    docker run –network my-bridge-network –name container-1 my-image
    docker run –network my-bridge-network –name container-2 my-image

  3. 覆盖网络（overlay network）：
    覆盖网络允许在多个Docker主机上的容器之间建立通信。这对于在分布式应用程序中进行容器编排（如使用Docker Swarm或Kubernetes）非常有用。覆盖网络使用VXLAN（Virtual eXtensible LAN）技术，将容器通信封装在UDP包中，允许在不同主机之间透明地进行通信。
    docker network create –driver overlay my-overlay-network
    使用覆盖网络的容器：
    docker service create –name service-1 –network my-overlay-network my-image
    docker service create –name service-2 –network my-overlay-network my-image
    容器之间的通信：
    通过IP地址进行通信：
    在默认网络或桥接网络中，容器可以通过其分配的IP地址相互通信。例如，在默认网络中，容器A可以通过容器B的IP地址访问它。

    通过IP地址进行通信

    curl http://<容器B的IP>:<容器B的端口>
    通过容器名称进行通信：
    在Docker中，容器名称会映射到容器的IP地址。因此，在同一网络中，容器可以通过其名称进行通信。

    通过容器名称进行通信

    curl http://<容器B的名称>:<容器B的端口>
    通过服务名称进行通信（覆盖网络）：
    在覆盖网络中，使用服务名称进行通信，而不是直接使用容器名称。服务名称是覆盖网络上的唯一标识符。

    通过服务名称进行通信

    curl http://<服务B的名称>:<服务B的端口>
    这些网络模式提供了不同的方式来组织和管理容器之间的通信，可以根据具体的应用场景选择合适的网络模式。

数据卷可以用于持久化存储数据，使得数据不会丢失，即使容器被停止或删除。
多个容器可以共享同一个数据卷，实现容器之间的数据共享。
数据卷的内容可以在容器之间传递，并且可以在主机和容器之间进行数据同步。

Docker安全性：
请讨论Docker容器的安全性措施，包括如何限制容器的权限和减小攻击面。
Docker容器的安全性是一个重要的考虑因素，因为容器化环境的安全性直接关系到应用程序和数据的保护。以下是一些Docker容器的安全性措施，包括如何限制容器的权限和减小攻击面：

  1. 使用最小化的基础镜像：
    选择基础镜像时应该使用最小化的镜像，例如Alpine Linux等，以减小镜像的大小和减小潜在的攻击面。较小的镜像通常包含的软件和工具较少，因此减少了可能的安全漏洞。

  2. 定期更新基础镜像：
    定期更新使用的基础镜像，以包含最新的安全修复和更新。使用过时的基础镜像可能暴露容器于已知的安全漏洞。

  3. 避免以root用户身份运行容器：
    在Dockerfile中，避免使用
    USER root
    FROM ubuntu:latest

    避免使用 USER root

    USER myuser

  4. 使用容器健康检查：
    使用Docker容器的健康检查机制，确保容器内应用程序的运行状态。健康检查可以帮助自动监控和修复容器，从而提高容器的可用性和安全性。

  5. 精确控制容器的能力：
    使用Dockerfile中的

–cap-drop
–cap-add
–cap-drop
–cap-add
6. 使用AppArmor或SELinux：
在支持的系统上，启用AppArmor或SELinux以提供额外的安全层。这些安全模块可以限制容器的行为，减小容器对主机系统的潜在威胁。
7. 限制容器的资源：
使用Docker Compose或Docker Swarm等工具，可以限制容器使用的资源，如CPU、内存、磁盘空间等。这有助于防止容器占用过多的系统资源，减小拒绝服务攻击的可能性。
8. 网络隔离：
使用Docker网络隔离机制，通过将容器连接到桥接网络、覆盖网络或用户自定义网络，从而隔离容器之间的通信。防止容器直接暴露在主机的公共网络上，降低横向扩展攻击的风险。
9. 审查和监控：
审查容器的运行时行为，使用工具如Docker Bench Security、Clair等来扫描镜像并检测潜在的安全问题。使用日志和监控工具来记录和分析容器的活动，及时发现异常情况。
10. 保护敏感信息：
避免在Dockerfile中硬编码敏感信息（如密码、API密钥等），使用Docker Secrets或环境变量来传递敏感信息。确保这些信息在容器中得到适当的保护。
通过采取这些安全性措施，可以显著提高Docker容器环境的安全性，减小潜在攻击面，并确保应用程序和数据的安全。

Git基础知识：

你能简要解释Git的基本工作原理是什么吗？
Git的基本工作原理涉及三个主要区域：工作目录（Working Directory）、暂存区（Staging Area）和版本库（Repository）。
工作目录（Working Directory）：
工作目录是你本地文件系统中存储项目文件的地方。这是你进行实际文件修改的区域。
暂存区（Staging Area）：
暂存区是一个临时区域，用于存放你已经修改的文件，准备提交到版本库。在这里，你可以选择性地添加或移除文件，形成一组将要提交的修改。
版本库（Repository）：
版本库是Git中最重要的部分，它包含了项目的所有历史记录和元数据。版本库存储在项目的
.git
版本库分为两个部分：对象数据库和引用。
对象数据库包含了项目中的所有文件和目录的内容，以及与它们的版本历史相关的元数据。这些元数据以对象（objects）的形式存储。
引用（refs）是指向特定提交的指针，比如分支（branch）和标签（tag）。
基本的工作流程如下：
在工作目录中修改文件。
将修改的文件添加到暂存区。
将暂存区的文件提交到版本库，形成一个新的提交对象。
这一系列的提交对象形成了项目的版本历史。每个提交对象包含了指向上一个提交的引用，从而构成了一个有向无环图，这就是Git的版本控制树。Git通过跟踪这个树状结构来记录项目的演变和修改历史。

Git中的“暂存区”是什么，它有什么作用？
暂存区的作用包括：
精细控制提交内容：
通过暂存区，你可以选择性地添加和提交文件的部分修改，而不是一次性提交所有的更改。这提供了更灵活的版本控制。
避免意外提交：
暂存区允许你审查和确认将要提交的修改，减少了意外提交不必要的或未经测试的更改的可能性。
支持协作：
在团队协作中，暂存区允许每个开发者根据自己的需求将更改添加到提交中，从而更好地协同工作。
在命令行中，你可以使用git add命令将文件或修改添加到暂存区，然后使用git commit命令将暂存区的内容提交到版本库。

分支管理：

你能解释Git分支的概念吗？在项目中如何使用分支？
在Git中，分支是一个独立的、可用于并行开发的工作流。它允许你在项目中同时处理多个版本，而不会影响主线或其他分支。每个分支都是项目中的一个独立的指针，指向项目历史中的一个提交。
以下是关于Git分支的基本概念和在项目中如何使用分支的解释：

新功能开发：

合并与解决冲突：

你如何将一个分支的更改合并到另一个分支？
要将一个分支的更改合并到另一个分支，你可以使用Git的git merge命令。以下是基本的步骤：
确保你在目标分支上：
在执行合并之前，确保你在要接收更改的目标分支上。你可以使用git checkout（或git switch）切换到目标分支，例如：
git checkout target_branch
或者
git switch target_branch
请注意，target_branch是你想要将更改合并到的分支的名称。
执行合并命令：
一旦你在目标分支上，执行合并命令：
git merge source_branch
这里，source_branch是包含你想要合并更改的分支的名称。
例如，如果你在主分支上，想要将feature-branch的更改合并到主分支，你可以执行：
git merge feature-branch
解决合并冲突（如果有）：
如果Git能够自动合并更改，那么它会直接完成合并。但是，如果有冲突，Git将提示你解决冲突。你需要手动编辑冲突的文件，选择要保留的更改，然后标记冲突已解决。
提交合并结果：
一旦解决了冲突，使用git add命令将解决冲突的文件标记为已解决，然后执行：
git commit
这将提交合并的结果，包括解决冲突的更改。
通过以上步骤，你就成功将一个分支的更改合并到另一个分支。这是协作团队中常见的操作，允许不同开发者在不同的分支上进行独立的工作，并在需要时将他们的更改合并到主分支或其他目标分支。

如果在合并分支时发生冲突，你会如何解决？
解决合并冲突是Git中常见的任务，通常需要手动介入以确保正确的合并。以下是解决合并冲突的一般步骤：
检测合并冲突：
当你执行git merge命令并存在冲突时，Git会停止合并并标记有冲突的文件。在这些文件中，Git会用特殊标记标识出冲突的地方。
手动解决冲突：
打开有冲突的文件，你会看到类似以下的标记：
<<<<<<< HEAD
// 代码来自目标分支（通常是当前分支）
=======
// 代码来自要合并的分支

source_branch
你需要手动编辑这些标记之间的代码，选择保留目标分支的更改，要合并的更改，或两者的组合。删除冲突标记后，文件应该包含你想要的最终结果。
标记文件为已解决：
一旦你手动解决了冲突，使用以下命令标记文件为已解决：
git add conflicted_file
这将告诉Git你已经解决了文件中的冲突。
继续合并：
完成所有冲突文件的解决后，继续合并操作：
git merge –continue
或者使用 git commit 来提交合并结果。
取消合并（如果需要）：
如果你在解决冲突的过程中发现合并出现了问题，可以使用以下命令取消合并操作：
git merge –abort
这会放弃当前的合并操作，并将你的工作目录恢复到合并前的状态。
以上步骤是一般情况下解决合并冲突的方式。在团队协作中，及时解决合并冲突并保持代码库的干净状态是非常重要的。

撤销更改：

如何撤销在工作目录中的未提交更改？
如果你在工作目录中做了一些修改但尚未提交，并希望撤销这些未提交的更改，可以使用git checkout或git restore命令。以下是两种方法：
方法一：使用 git checkout
使用 git checkout 可以撤销对单个文件或整个目录的更改。
撤销单个文件的更改：
git checkout – file_name
此命令将丢弃对指定文件的更改，恢复到最近的提交状态。
撤销整个目录的更改：
git checkout – path/to/directory/
这将撤销指定目录下所有文件的更改。
方法二：使用 git restore
git restore 是较新版本的 Git 中引入的命令，用于还原工作目录中的更改。
撤销单个文件的更改：
git restore –source=HEAD –staged –worktree file_name
这将从最近的提交（HEAD）还原文件的更改。
撤销整个目录的更改：
git restore –source=HEAD –staged –worktree path/to/directory/
这将从最近的提交还原指定目录下所有文件的更改。
请注意，git restore 的参数 –source=HEAD 表示使用最近的提交作为还原的源头。–staged 表示将文件的更改从暂存区（索引）还原到工作目录，–worktree 表示将文件的更改从工作目录还原到最近的提交状态。
选择使用哪种方法取决于你所使用的 Git 版本和个人偏好。在新的项目中，git restore 是更为现代的选择。

如果已经提交了更改，你如何回滚到之前的版本？
如果已经提交了更改，而你想要回滚到之前的版本，可以使用 git reset 或 git revert 命令。这两个命令有不同的用途，具体取决于你的需求。
方法一：使用 git reset
使用 git reset 可以将分支的 HEAD 指针和工作目录回滚到指定的提交。请注意，git reset 会改变历史记录，因此在协作项目中慎用，特别是在已经推送到远程仓库的提交上。

将 HEAD 指针和工作目录都回滚到指定的提交

git reset –hard commit_hash
这将使得工作目录和仓库状态回到指定提交，并且之后的提交将被丢弃。
方法二：使用 git revert
使用 git revert 可以创建一个新的提交，该提交撤销指定提交引入的更改。这种方法更安全，因为它不会修改历史记录，而是创建新的提交来撤销之前的更改。

创建一个新的提交，撤销指定提交的更改

git revert commit_hash
这会打开一个编辑器以输入提交信息。保存并关闭编辑器后，将创建一个新的提交，该提交撤销了指定提交的更改。
选择使用哪种方法取决于你的具体需求。如果你希望彻底删除历史记录中的一些提交，可能使用 git reset。如果你希望保留历史记录并且有能够撤销撤销的可能性，可能使用 git revert 更为安全。

远程仓库：

怎样将本地仓库连接到远程仓库？
将本地仓库连接到远程仓库通常涉及两个主要步骤：添加远程仓库地址和推送到远程仓库。以下是一般的步骤：
步骤一：添加远程仓库地址
使用 git remote add 命令来添加远程仓库地址。常见的约定是将远程仓库命名为 origin，但你可以选择其他名称。
git remote add origin <远程仓库地址>
例如：
git remote add origin https://github.com/你的用户名/你的仓库名.git
步骤二：推送到远程仓库
使用 git push 命令将本地分支的更改推送到远程仓库。通常，你需要指定本地分支的名称和远程仓库的名称（在此例中，通常是 origin）。
git push -u origin <本地分支名称>
例如，如果你要推送到主分支：
git push -u origin main
上述命令中的 -u 选项用于设置上游（upstream）分支，使得以后的推送和拉取都能与该分支关联。
如果你是第一次推送，还可以使用 -u 选项简写为：
git push -u origin main
一旦远程仓库连接并推送，你就可以通过以下命令查看连接的远程仓库：
git remote -v
这将显示你的本地仓库连接的所有远程仓库地址及其用途。
请确保你有正确的权限来推送到远程仓库。如果你是通过 HTTPS 连接的，可能需要提供用户名和密码。如果通过 SSH 连接，你需要设置SSH密钥。
你如何从远程仓库拉取最新的更改？
从远程仓库拉取最新的更改通常使用 git pull 命令。以下是一般的步骤：
git pull origin <远程分支名称>
这个命令将从指定的远程仓库（通常是 origin）的指定分支（通常是主分支，比如 main 或 master）拉取最新的更改并合并到当前本地分支。
如果你已经设置了上游分支（通常在推送时使用 -u 或 –set-upstream 选项），你可以简化命令：
git pull
这个命令等同于：
git pull origin <当前本地分支名称>
请注意，git pull 实际上执行两个操作：git fetch 和 git merge。git fetch 用于获取远程仓库的最新更改，而 git merge 用于将这些更改合并到你的本地分支。
如果你希望只获取远程仓库的最新更改而不自动合并，可以使用 git fetch：
git fetch origin
这样，你可以查看最新的远程更改，并选择是否要手动合并到本地分支。
总之，git pull 是一个方便的命令，适用于从远程仓库拉取并合并最新的更改。

子模块的作用：
模块化开发：
子模块使得项目可以模块化开发，将不同的功能或组件拆分成独立的仓库，并在主项目中引入这些子模块。

子模块允许你在主项目中独立地更新子模块的内容。这使得项目能够使用最新的子模块版本，而不必等待整个项目的发布。

git submodule add <仓库URL> <目标路径>

这将递归地克隆主项目和所有子模块。

这会拉取每个子模块的最新更改。

JMeter的断言和提取器是什么？请解释它们的作用和用法。
在JMeter中，断言（Assertions）和提取器（Extractors）是两个重要的组件，用于验证响应结果和提取关键数据。以下是它们的作用和用法的详细解释：
断言（Assertions）： 断言用于验证服务器的响应结果是否符合预期。它可以检查响应的各个方面，如响应码、响应头、响应数据等。断言的作用是帮助确认服务器是否按照预期返回正确的结果，以便判断测试是否通过。
在JMeter中，提供了多种断言类型，包括以下几种常用的断言：

  1. 响应断言（Response Assertion）： 用于验证响应数据中是否包含指定的文本、正则表达式、XML或JSON等内容。
  2. 响应码断言（Response Code Assertion）： 用于验证响应的HTTP状态码是否符合预期。
  3. 响应头断言（Response Headers Assertion）： 用于验证响应的HTTP头部信息是否符合预期。
  4. XML断言（XML Assertion）： 用于验证响应数据是否符合指定的XML结构和内容。
  5. JSON断言（JSON Assertion）： 用于验证响应数据是否符合指定的JSON结构和内容。
    通过添加适当的断言，可以对响应结果进行验证，确保系统的正确性和一致性。
    提取器（Extractors）： 提取器用于从服务器响应中提取关键数据，并将其存储到变量中，以便在后续的请求中使用。它可以从响应的文本、正则表达式、XML或JSON等数据中提取所需的内容，如会话ID、表单参数等。
    在JMeter中，提供了多种提取器类型，包括以下几种常用的提取器：
  6. 正则表达式提取器（Regular Expression Extractor）： 用于从响应的文本中使用正则表达式提取指定的内容。
  7. CSS/JQuery提取器（CSS/JQuery Extractor）： 用于从HTML或XML响应中使用CSS选择器或JQuery表达式提取指定的内容。
  8. JSON提取器（JSON Extractor）： 用于从JSON响应中提取指定的内容。
    通过添加适当的提取器，可以从响应结果中提取所需的数据，以便在后续的请求中使用，如动态参数传递、会话维持等。
    断言和提取器是JMeter中常用的工具，用于验证响应结果的正确性和提取关键数据。它们的正确使用可以帮助测试人员更好地进行性能测试和功能测试，并提供更准确的测试结果。

性能测试是在软件开发过程中对系统、应用程序或组件进行测试，以评估它们在不同负载条件下的性能和响应能力。它旨在检测系统在现实使用场景下的性能瓶颈、资源利用率、稳定性和可靠性。
性能测试在软件开发生命周期中非常重要。以下是其重要性的一些方面：

  1. 用户体验改善：性能测试可以确保系统在预期的负载下以可接受的速度响应用户请求。通过检测和解决性能问题，可以提高用户的满意度和体验，避免用户因为系统响应慢而流失。
  2. 可扩展性评估：性能测试可以评估系统在面对持续增长的用户和数据负载时的可扩展性。它帮助确定系统是否能够有效地处理大规模的并发请求，支持业务的发展和扩展。
  3. 资源规划和优化：性能测试可以帮助识别系统的瓶颈和性能瓶颈，例如内存、CPU、网络带宽等资源的使用情况。通过分析测试结果，可以优化资源分配和利用，提高系统的效率和性能。

请解释什么是负载测试和压力测试，它们之间有什么区别？
负载测试和压力测试是性能测试中常用的两种测试类型，它们有一些区别，下面我将详细解释：

  1. 负载测试：负载测试是在模拟实际使用条件下对系统或应用程序进行测试，以评估其在不同负载条件下的性能表现。它的目的是确定系统在正常负载下的性能瓶颈、资源利用率和响应能力。负载测试通常涉及模拟用户数量、事务量和数据量等因素的变化。通过逐渐增加负载，负载测试可以确定系统的承载能力、稳定性和可靠性。
  2. 压力测试：压力测试是对系统施加高压力负载的测试，以评估系统在极限负载下的性能表现。它的目的是验证系统的弹性、稳定性和极限容量。压力测试模拟系统在高负载条件下的行为，可以是突发访问量增加、高并发请求或持续高负载等情况。压力测试的目标是找出系统的性能极限、瓶颈和潜在问题。
    区别：
    ● 目的：负载测试的目的是评估系统在正常负载下的性能和响应能力，而压力测试的目的是验证系统在高压力负载下的弹性和稳定性。
    ● 负载水平：负载测试涉及不同负载水平的模拟，以覆盖实际使用场景。而压力测试施加高压力负载，以达到系统的极限容量。
    ● 测试时间：负载测试通常是长时间运行的，以模拟真实的使用情况。而压力测试通常是短时间内对系统施加高负载，以验证系统的极限容量。
    ● 结果分析：负载测试的结果主要用于确定系统的性能瓶颈和优化机会。而压力测试的结果主要用于验证系统是否能够在高压力负载下保持稳定和可靠。
    综上所述，负载测试和压力测试是两种不同的性能测试类型。负载测试旨在评估系统在正常负载下的性能表现，而压力测试旨在验证系统在高压力负载下的弹性和稳定性。它们的选择取决于测试目标和所需的性能指标。

如何确定性能测试的目标和指标？请列举几个常用的性能指标，并解释其含义。
确定性能测试的目标和指标是性能测试过程中非常重要的一步，它们可以根据系统需求和用户期望来确定。以下是几个常用的性能指标，并解释其含义：

  1. 响应时间：响应时间是从用户发起请求到系统返回响应的时间间隔。它衡量了系统对用户请求的快速响应能力。较低的响应时间表示系统性能较好，用户能够快速获得结果。
  2. 吞吐量：吞吐量是指在特定时间内系统能够处理的请求数量。它衡量了系统的处理能力和效率。较高的吞吐量表示系统可以处理更多的并发请求。
  3. 并发用户数：并发用户数指同时访问系统的用户数量。它衡量了系统在同一时间段内能够处理的并发请求。测试中通过增加并发用户数来逼近或达到系统的承载极限。
  4. 资源利用率：资源利用率是指系统在处理请求时所使用的硬件资源的利用情况。它可以包括CPU利用率、内存利用率、网络带宽利用率等。通过监测资源利用率，可以评估系统在不同负载条件下的资源消耗情况，确定系统的性能瓶颈。
  5. 错误率：错误率是指在测试过程中发生的错误或失败的请求的比例。它可以衡量系统在高负载或极限负载下的稳定性和可靠性。较低的错误率表示系统能够在负载压力下正常运行。
  6. 并发性能：并发性能是指系统在处理大量并发请求时的稳定性和响应能力。它衡量了系统在高负载条件下的性能表现和承载能力。
    以上是常用的性能指标，根据具体的系统和应用，还可以根据需求确定其他相关指标。在确定性能测试的目标和指标时，需要与利益相关者（如开发团队、产品经理等）进行充分沟通，了解他们的期望和需求，以确保测试的准确性和有效性。

  5. 数据库性能问题：数据库通常是系统性能的关键因素之一。在性能测试中，我经常遇到数据库方面的问题，如慢查询、缺乏索引、数据库连接问题等。为了解决这些问题，我会使用数据库性能监控工具来分析数据库的查询性能、索引使用情况和连接池利用率。然后，我会优化查询语句、添加适当的索引、调整数据库配置或增加数据库服务器容量。

请解释什么是性能剖析和性能调优，以及它们在性能测试中的作用。
性能剖析（Profiling）和性能调优（Performance Tuning）是性能测试中重要的概念，它们都与改进系统的性能和效率有关。

  1. 性能剖析：性能剖析是一种通过监测和分析系统的运行时行为来识别性能瓶颈和优化机会的方法。它可以帮助开发人员和测试人员深入了解系统在不同负载条件下的性能特征和资源利用情况。性能剖析通常包括以下方面：
    ○ 代码剖析：通过检查代码的执行路径、函数调用和运行时间等信息，来确定哪些代码部分消耗了较多的时间和资源。
    ○ 内存剖析：通过分析系统的内存使用情况，确定内存泄漏、非优化的对象创建和销毁等问题。
    ○ CPU剖析：通过监控CPU使用率、函数调用和线程活动，确定CPU密集型操作和性能瓶颈。
    ○ I/O剖析：通过监控I/O操作（如磁盘读写、网络传输等）的时间和频率，确定I/O瓶颈和资源利用不足。
    性能剖析可以帮助定位系统的性能瓶颈和瓶颈点，并为性能调优提供有价值的信息和指导。
  2. 性能调优：性能调优是一种通过优化系统的设计、代码和配置等方面来提高系统的性能和效率的过程。性能调优的目标是减少响应时间、提高吞吐量、降低资源消耗等，以满足用户的需求和提升用户体验。性能调优通常包括以下方面：
    ○ 代码优化：通过改进算法、减少不必要的计算和优化关键代码，来提高代码的执行效率和性能。
    ○ 数据库优化：通过优化查询语句、增加索引、调整数据库配置等手段，提升数据库的读写性能和响应速度。
    ○ 系统配置优化：通过调整系统的资源分配、缓存设置和线程池等配置，来优化系统的性能和承载能力。
    ○ 缓存和负载均衡：通过使用缓存和负载均衡技术，减轻服务器的负载压力，提高系统的吞吐量和并发处理能力。
    性能调优需要结合性能剖析的结果和实际的性能测试数据，针对性地优化系统的关键部分，以达到性能目标。
    性能剖析和性能调优在性能测试中起着关键的作用。通过性能剖析，我们可以识别系统中的性能瓶颈和优化机会，并确定优化的重点。然后，通过性能调优，我们可以针对性地优化系统的设计、代码和配置等方面，以提高系统的性能和效率。通过这两个步骤的结合，我们可以持续改进系统的性能，满足用户的需求并提供更好的用户体验。

事务

什么是事务

  • 一个事务就是一个完整的业务逻辑（业务流程），是一个最小的工作单元，不可再分。

    例子
    假设转账，从A账户向B账户中转账10000。将A账户的钱减去10000，B账户的钱加上10000
    这就是一个完整的事务逻辑。

以上的操作是一个最小的工作单元，==要么同时成功，要么同时失败，不可再分==。

和事务有关的语句

只有DML语句中的insert、delete、update和事务有关，其他都无关系。
因为只有以上的三个语句是数据库表中数据进行增、删、改的。
只要你的操作一旦涉及到数据的增、删、改，那么就一定要考虑事务。

思考题

  • 假设所有的业务，只要一条DML语句就能完成，还有必要存在事务机制吗？
    正是因为做某件事的时候，需要多条DML语句共同联合起来才能完成，所以需要事务的存在，如果任何意见负载的事都能一条DML语句搞定，那么事务则没有存在的价值了。

到底什么是事务呢？

  • 说到底，一个事务其实就是多条DML语句同时成功或者同时失败
  • 事务就是批量的DML语句同时成功或者同时失败。

事务的4个特性

原子性

说明事务是最小的工作单元。不可再分。

一致性

所有事务要求，在同一个事务当中，所有操作必须同时成功；或者同时失败，以保证数据的一致性。

隔离性

A事务和B事务之间具有一定的隔离。

A事务在操作一张表的时候，另一个事务B也操作这张表会怎样？

持久性

事务最终结束的一个保障。事务提交，就相当于把没有保存到硬盘上的数据保存到了硬盘上。

事务的隔离性

A教室和B教室中间有一道墙，这道墙可以很厚，也可以很薄。这就是事务的隔离级别。这道墙越厚,表示福离级别就越高。

隔离级别

读未提交 read uncommitted（最低级别）

事务A可以读取到事务B未提交的数据。这种现象称为==脏读现象==。

  • ==没有提交就读到数据==

  • 这种隔离级别一般都是理论上的，大多数的数据库隔离级别都是二档起步!（==读已提交==）

读已提交 read committed

事务A只能读取到事务B提交的数据。

  • ==提交之后才能读到数据==

  • ==解决了脏读==现象。

  • 这种级别存在==不可重复读取==数据问题

    在同一个事务中，同一个读操作对同一个数据的前后两次读取产生了不同的结果，这就是不可重复读。在事务开启之后,第一次读到的数据是3条，当前事务还没有结束，可能第三次再读取的时候，读到的数据是4条，3不等于4称为不可重复读取。

  • 这种隔离级别是比较真实的数据,每一次读到的数据是绝对的真实。

  • oracle数据库默认的隔离级别是: read comaitted

可重复读 repeatable read

事务A开启之后,不管是多久，每一次在事务A中读取到的数据都是一致的，即使事务B将数据已经修改，并且提交了，事务A读取到的数据还是没有发生改变,这就是可重复读。

  • ==提交之后也读不到，永远读取的都是开启事务时的数据==

    早上9点开启的事务，到了晚上9点读取的数据还是早上9点的数据

  • ==解决了不可重复==读取的问题

  • 这种级别存在的问题是出现==幻象读==

    每一次读取的数据都是幻象，不够真实。

  • Mysql默认隔离级别就是可重复读

序列化/串行化 serializable（最高级别）

这是最高隔离级别,效率最低。解决了所有的问题。

  • 这种隔离级别表示事务排队。不能并发!

    不能并发：对一个事务不能同时处理

  • 每一次读取到的数据都是最真实的，并且效率是最低的。

索引

什么是索引

  • 索引是在数据库的字段上添加的，是为了提高查询效率存在的一种机制。
  • 一张表的一个字段可以添加一个索引，当然，多个字段联合起来也可以添加索引。
  • 索引相当于一本书的目录，是为了缩小扫描范围而存在的一种机制。

例子

表名：t_user
| id | name | email | address | |
| —- | ——– | —– | ——- | —- |
| 1 | zhangsan | | | |
| 2 | lisi | | | |
| 3 | wangwu | | | |
| 4 | dajun | | | |
| 5 | dilireba | | | |

  • 以上的这条SQL语句会去name字段上扫描。如果name字段上没有索引或者没有给name字段创建索引，MySQL会进行全扫描，会将name字段上的每一个值都比对一遍。效率较低。

MySQL查询方式

  • 全表扫描
  • 根据索引检索

索引的实现原理

索引的实现原理就是缩小扫描的范围，避免全表扫描。

例子

id(PK)name

提醒1：在任何数据库当中主键上都会自动添加索引对象。另外在mysql中，一个字段上如果有unique约束的话，也会自动创建索引对象。
提醒2：在任何数据库中，任何一张表的任何一条记录在硬盘存储上都有一个硬盘的物理存储编号。
提醒3：在mysql中，索引是一个单独的对象，不同的存储引擎以不同的形式存在。在MyISAM存储引擎中，索引存储在一个.MYI文件中，在InnoDB存储引擎中，索引存储在一个逻辑名称叫做tablespace的当中。在MEMORY存储引擎当中索引被存储在内存当中。不管索引存储在哪里，索引在mysql当中都是一个树的形式存在。（自平衡二叉树：B-Tree）

mysql发现id字段上有索引对象，所以会通过索引对象idindex进行查找。

注意

  • 索引也是需要排序的，因为只有排序了才会有区间查找这一说（缩小扫描范围其实就是扫描某个区间）。
  • 并且这个索引的排序和TreeSet数据结构相同。TreeSet（TreeMap）底层就是一个自平衡的二叉树！在mysql当中索引是一个B-Tree数据结构。
  • 遵循左小右大原则存放。采用中序遍历方式遍历数据。
  • 在mysql当中，主键、unique字段都会自动添加索引的

什么时候添加索引？

  • 数据量庞大
    数据量庞大需要测试，因为每一个硬件环境不同。
  • 该字段经常出现在where后面，以条件形式存在，经常被扫描
  • 该字段很少DML操作（insert、delete、update）。因为DML操作后，索引需要重新排序

建议不要随意添加索引，因为索引也是需要维护的，太多的话反而会降低系统的性能。
建议通过主键查询，通过unique约束的字段进行查询，效率较高。

df 命令获得真正的文件系统数据，而 du 命令只查看文件系统的部分情况。

4.linux系统里，您知道buffer和cache如何区分吗？

buffer和cache都是内存中的一块区域，当CPU需要写数据到磁盘时，由于磁盘速度比较慢，所以CPU先把数据存进buffer，然后CPU去执行其他任务，buffer中的数据会定期写入磁盘；当CPU需要从磁盘读入数据时，由于磁盘速度比较慢，可以把即将用到的数据提前存入cache，CPU直接从Cache中拿数据要快的多。

/var 某些大文件的溢出区，比方说各种服务的日志文件
/usr 最庞大的目录，要用到的应用程序和文件几乎都在这个目录。其中包含： /usr/X11R6 存放X window的目录 /usr/bin 众多的应用程序 /usr/sbin 超级用户的一些管理程序 /usr/doc linux文档 /usr/include linux下开发和编译应用程序所需要的头文件 /usr/lib 常用的动态链接库和软件包的配置文件 /usr/man 帮助文档 /usr/src 源代码，linux内核的源代码就放在/usr/src/linux里 /usr/local/bin 本地增加的命令 /usr/local/lib 本地增加的库
